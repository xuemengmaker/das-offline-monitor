# DAS 离线回放系统接口契约与测试策略

## 1. 实际边界

本项目是历史 TDMS 的离线回放系统，不拥有真实 DAS 采集仪或厂商通信协议。因此“采集端”定义为一个**本地软件适配契约**，用于验证监测软件在接收设备状态和 TDMS 文件交接信息时的行为；它不是硬件联调证明。

```text
本地采集端模拟器 / 历史 TDMS
          | 数据资产注册、设备心跳
          v
FastAPI 监测服务 ---- 分析任务/结果查询 ----> 浏览器操作台、Postman
          |
          | 持续性预警事件 Webhook
          v
本地 HTTP 告警接收端（自动化测试中真实启动）
```

## 2. 接口清单

| 边界 | 接口 | 目的 | 关键验证 |
|---|---|---|---|
| 数据接入 -> 监测服务 | `POST /api/v1/data-assets/register` | 登记已落盘 TDMS | 路径白名单、TDMS 元数据、去重、可选 SHA-256 |
| 操作台 -> 监测服务 | `POST /api/v1/analysis-jobs` | 创建离线分析任务 | 202、参数校验、可使用 `data_asset_id` |
| 操作台 -> 监测服务 | `GET /api/v1/analysis-jobs/{job_id}` | 轮询任务状态/结果 | queued/running/completed/failed、job_id 可追溯 |
| 采集端模拟器 -> 监测服务 | `POST /api/v1/devices/heartbeats` | 上报采集状态 | 在线状态、通道数、采样率、最新数据路径 |
| 监测服务 -> 告警接收端 | HTTP Webhook | 投递持续性风险事件 | JSON 契约、事件 ID、2xx 成功、5xx/连接失败最多 3 次 |
| 操作台 -> 监测服务 | `GET /api/v1/alarm-events` | 查询事件与投递结果 | 事件与任务关联、投递状态和次数 |

## 3. 典型流程

1. 数据文件落入约定的数据根目录，采集端通过数据资产注册接口交接相对路径。
2. 服务读取 TDMS 元数据，保存资产清单；相同文件版本重复注册返回同一资产 ID。
3. 操作台以 `data_asset_id` 创建分析任务，服务将资产映射回受限目录内的相对路径。
4. 分析任务完成后，持续性规则产生的预警写入事件表；没有持续性预警则不投递告警。
5. 若配置告警接收端，服务携带 `X-Event-Id` 和 JSON 事件投递。接收端 2xx 表示成功；5xx 或连接失败会在有限次数内重试，并保存最终投递记录。

## 4. 自动化测试分层

| 层级 | 当前覆盖 | 目的 |
|---|---|---|
| 信号/TDMS单元测试 | 有界读取、候选、通道区间、持续性、跨文件持续性 | 验证算法与文件读取规则 |
| API契约测试 | 请求参数、任务状态、路径安全、CSV | 验证调用方与服务端约定 |
| 系统接口测试 | 资产登记/去重/完整性、心跳、资产驱动分析 | 验证各模块交接 |
| 端到端告警投递 | 启动本地 HTTP 接收端，验证 JSON、事件 ID、5xx 重试 | 验证服务到下游告警接收端 |

运行：

```bash
.venv/bin/python -m pytest -q --alluredir=report/allure-results
```

## 5. 生产落地边界

- 生产环境需要根据真实采集仪供应商文档实现协议适配器，并完成设备、网络和现场联调；本仓库没有这些证据。
- Webhook 回调地址在生产环境必须使用白名单、认证、TLS、签名和队列/死信机制；本地演示仅验证 HTTP 契约和有限重试。
- TDMS 文件顺序在生产环境应以不可变采集时间戳为准，不能仅依赖文件名字典序。
